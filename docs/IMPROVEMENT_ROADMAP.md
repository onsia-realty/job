## 1. 이 문서의 목적과 사용법

Claude Code 또는 Codex CLI에서 프로젝트의 부족한 부분을 순서대로 보완하기 위한 실행 가능한 체크리스트다. 체크박스는 실제 검증 결과가 있을 때만 완료로 변경한다. 진행 중 발견한 문제·결정·범위 변경은 아래 작업 기록에 추가한다.

이 문서는 실행 권한을 부여하는 명령서가 아니다. 문서를 읽거나 평가하는 요청만으로 운영 DB 변경, 결제, 배포, 커밋을 실행하지 않는다. 사용자가 구현을 요청한 범위 안에서 진행한다.

시작 시 읽을 자료:

1. 저장소에 적용되는 지침 파일과 `CLAUDE.md`
2. `docs/HANDOFF_CODEX.md`
3. `PROGRESS.md`, `docs/stay-progress.md`
4. 이 문서와 현재 `git status`, 작업 대상의 실제 코드

문서와 코드가 다르면 현재 코드와 재검증 결과를 우선한다. 과거 기록의 DB 적용·배포 성공은 현재 환경에서 재확인하기 전까지 확정 사실로 취급하지 않는다.

## 2. 객관적 평가

부동산 실무자를 대상으로 구인구직, 시세지도, 단기임대, 콘텐츠를 결합한 후기 MVP~초기 운영 단계의 플랫폼이다. 구현 범위는 넓지만 핵심 사용자 흐름의 통합 검증과 운영 자동화가 뒤처져 있다.

| 항목 | 판단 | 근거와 제한 |
|---|---|---|
| 제품 방향 | 타깃은 명확하나 우선순위 분산 | 구인구직·지도·단기임대·AI·콘텐츠 동시 확장 |
| 기능 구현 | 상당 부분 구현 | 화면, API, Supabase, 외부 연동 코드 존재 |
| 흐름 완결성 | 보완 필요 | 인증 이후 등록, 승인, 결제, 문의의 전체 흐름 검증 부족 |
| 데이터 신뢰 | 보완 필요 | 샘플 혼재, 집계 갱신 미구현, 수동 배치 잔여 |
| 유지보수 | 기술부채 누적 | 큰 폼·페이지, 중복 로직, lint 오류 |
| 운영 준비 | 제한된 시험 운영에 적합 | 관리자 mock, 장애 감지·복구 검증 부족 |
| 보안 | 판정 보류 | 인증·자동 승인·RLS 경계에 추가 검증 필요 |

기능 구현 70~80%, 운영 준비 40~60%라는 평가는 정량 측정값이 아닌 잠정 추정이다. 사용자 수, 매출, 재방문, 문의 전환 자료는 확인하지 않았으므로 사업성은 평가하지 않았다.

- 조회 API의 데이터는 테스트·시드 자료일 수 있으므로 실제 고객 활동 건수로 해석하지 않는다.
- 기존 lint 수치는 정리의 출발점이며 영구 허용 기준이 아니다.

## 4. 작업 보존 및 검증 규칙

- 시작할 때 `git status --short --branch`와 대상 diff를 읽는다.
- 기존 Claude 작업은 사용자 소유다. 삭제·되돌리기·일괄 덮어쓰기를 하지 않는다.
- 중첩된 기존 작업을 수정해야 하면 diff를 이해하고 현재 동작을 보존하면서 필요한 부분만 수정한다.
- 분석·로컬 구현·운영 변경을 구분한다. 운영 SQL, 실결제, 발행, 배포, push는 명시된 요청 범위를 확인한다.
- `.env` 값과 토큰을 로그·문서·커밋에 기록하지 않는다. 환경변수는 필요한 키의 존재만 확인한다.
- 기존 dev 서버를 확인하고 중복 실행이나 무단 종료를 피한다. 동시 build가 dev 출력에 영향을 줄 가능성도 확인한다.
- 지도 변경은 브라우저 스크린샷과 상호작용으로 검증한다.
- HTTP 점검은 User-Agent를 지정하고 상태 코드와 기대 응답을 함께 확인한다.
- 단기임대 금액은 원 단위 `_won`, 시세 금액은 만원 단위다.
- 단기임대 서버 통제 필드를 Zod 화이트리스트에 추가하거나 `.passthrough()`로 풀지 않는다.
- 결제 가격은 `src/lib/toss.ts`를 단일 기준으로 유지한다.
- SQL 실행은 대상 Supabase 프로젝트와 적용 상태부터 확인한다. 앱과 별개 CRM 프로젝트를 혼동하지 않는다.

## 5. 권장 제품 방향

구인구직을 핵심 수익 흐름으로 완성하고, 시세지도·실무 도구를 반복 방문 이유로 강화한다. 단기임대는 소수 중개사·제한된 매물로 파일럿을 진행한다. 뉴스·AI 신규 확장은 핵심 흐름 안정화 이후 우선순위를 재평가한다.

측정할 지표:

- 공고 및 매물 등록 시작 대비 완료율
- 결제 시도 대비 승인 및 광고 적용 성공률
- 공고 조회 대비 지원율, 매물 조회 대비 문의율
- 등록 후 첫 지원·문의까지 걸린 시간
- 재방문율, 승인 처리 시간, 오류율

개인정보나 인증 토큰을 분석 이벤트에 포함하지 않는다. 현재 지표 수집 여부부터 확인한다.

- [ ] 기존 백업을 보존하면서 lint 범위와 운영 코드 품질 기준을 정리한다.
- [ ] 큰 폼·페이지에서 데이터 처리와 표시 로직을 필요한 범위부터 분리한다.
- [ ] 핵심 흐름의 통합 테스트를 추가한다. 구현을 복제하는 테스트는 피한다.
- [ ] 서버 오류·배치 실패·결제 불일치의 감지와 알림 경로를 마련한다.
- [ ] DB 백업·복구 및 배포 롤백 절차를 확인하고 테스트 환경에서 연습한다.
- [ ] 지도 로딩·검색·폼 제출·모바일 속도를 측정한 후 병목을 개선한다.
- [ ] README, PROGRESS, HANDOFF의 상태·명령·검증 수치를 동기화한다.

완료 기준: 기능 수정 시 회귀를 발견할 수 있고, 운영 오류를 발견·추적·복구할 수 있다.

## 9. 예상 일정

가정: 경험 있는 개발자 1명과 AI 도구, 하루 집중 작업 약 6시간, 당일 의사결정 및 테스트 계정 제공. 신규 디자인 전면 개편·신규 대형 기능·외부 심사 대기는 제외한다. 확정 견적이 아니며 P0 점검 후 재산정한다.

| 단계 | 예상 작업일 |
|---|---:|
| 핵심 위험 점검 및 수정 범위 확정 | 3~5일 |
| 현재 stay 흐름 마무리 | 4~7일 |
| 데이터·자동화 정비 | 3~6일 |
| 관리자·문의 운영 기능 | 5~10일 |
| 통합·모바일·장애 복구 검증 | 5~8일 |
| 합계 | 20~36일, 약 4~7주 |

- 제한된 파일럿: 핵심 위험 해소를 전제로 약 1~2주.
- 초기 유료 운영 확대: 약 4~7주.
- 전체 기능 UX·운영·유지보수 정돈: 약 2~3개월 이상.
- 심각한 권한/결제 결함, DB 불일치, 인증 정책 변경은 별도 일정이 필요하다.
